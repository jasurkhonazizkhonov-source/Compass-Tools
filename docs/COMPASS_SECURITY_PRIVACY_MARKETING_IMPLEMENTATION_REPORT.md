## 2. Failed sign-ins (Admin only)

## 3. Customer email privacy

**Policy** (`src/server/privacy/customer-email.ts`, the one place that decides): Administrators and users with *Unlimited Customer Email Access* see complete customer addresses; **every other role is masked by default** (`j********h@gmail.com`: first and last character of the local part and the domain are kept; short and malformed values fall back safely). The permission is read fresh from the database on every decision, so revoking it applies on the next request; an unreadable permission fails closed (masked).

> **Updated 2026-11-22:** the allowance and the visibility of a revealed address now reset together at **1:15 PM `America/Los_Angeles`** (not midnight): the stored `dayKey` is a reveal-period key (`p` + the Pacific date the period started, e.g. `p20261122`), so no migration was needed; see `SECURITY_POSTURE.md` section 11. The text below describes the mechanism, which is unchanged apart from the key.

**Reveal allowance.** A restricted user may reveal the complete addresses of 5 customers per business day (`America/Los_Angeles`). Implementation: one transaction that (1) inserts a unique `(user, contact, day)` reveal row `ON CONFLICT DO NOTHING` (a repeat reveal of the same customer is free and race-proof), (2) advances the per-user per-day counter with a single `INSERT .. ON CONFLICT DO UPDATE .. WHERE count < 5 RETURNING`, (3) rolls everything back when the counter refuses, and writes an audit entry (actor, contact id, method, day; **never the address**). A failed read rolls back without consuming allowance. The response of the Reveal action carries no address: the page is re-rendered by the server.

**Exposure map** (where an address could reach a restricted user, and what now happens):

| Path | Result |
| --- | --- |
| Lead / contact detail pages (info card, primary email, email list, activity timeline) | masked until revealed; reveal button + "n / 5 used today" |
| Leads / contacts lists, referral picker, task lead-picker, global search | masked; **search never matches on email text for a restricted viewer** (a partial match is an oracle that reconstructs the address) |
| Email composer (lead, contact), quote send picker, sequence enrollment picker, airline-confirmation dialog | recipients are named by opaque id; the server resolves the address; a **raw address from a restricted user is refused** (it would be a probe for "is this address on file?"); an id of another customer is refused; confirmations show masked addresses |
| Quotes page, booking page, signed booking details, New Lead dialog, duplicate-contact lookup | masked; New Lead for an existing customer no longer needs the address retyped, and a masked value echoed back is never stored |
| Sequence enrollments table (per-enrollment recipient) | masked |
| Lead offer modal (polled) | masked |
| Activity timeline "load more" action and the dashboard activity feed | **masked (added in this audit; both leaked)** |
| Direct calls to server actions | the same checks run server-side; UI hiding is never the control |
| Logs / errors | only error categories are logged; no address in any new log line |
| **Staff notification emails** (New Flight Request, lead and contact reassignment, Booking Form Signed) | **RESOLVED 2026-11-22.** These used to carry the complete address and a mailto Reply button to the recipient mailbox, bypassing the reveal allowance. Now each recipient is checked fresh against the database (`recipientsMaySeeCustomerEmail`): an Administrator or a user with Unlimited Customer Email Access gets the email exactly as before; anyone else gets a one-line note ("Hidden for privacy - open the record in the CRM and use Reveal") instead of the address, with **no mailto link and no Reply button**; name, trip, itinerary, phone and the Call button are unchanged. A message sent to several people (Booking Form Signed) shows the address only if **every** recipient may see it. An unreadable permission or an unknown recipient hides it (fail closed). The builders produce **HTML only - no plain-text alternative exists**, so there is no second body; subjects, the notification log and error logs never contain the address (tested). The New Sale (profit) notification never contained the customer address. The customer-facing confirmation emails go to the customer and are unaffected. |
| Bulk contact import duplicate report | echoes only addresses the user typed; reveals nothing new |
| Get in Touch / CRM inquiries | Administrator only already |
| Subscriber lists | Administrator and Marketing Agent (existing business rule, unchanged). These are marketing audiences, not CRM customer records; the page does not read Contacts/Leads. |

**Not covered / limits.** Free-text notes that an agent typed an address into are user content and are not rewritten. The EmailLog `toEmail` column holds complete addresses (no UI reads it for restricted users today). Masking is applied where the data is shaped for the browser; a future page that selects `primaryEmail` and passes it to a client component must go through `withEmailPrivacy` / `buildContactEmailView`.

**Admin toggle.** `Users` page column "Unlimited Customer Email Access", default OFF, Administrators show a fixed "Always". Server action `updateUnlimitedCustomerEmailAccess`: Administrator only, same company only, refused for an Administrator target, enabling needs the recent-sign-in step-up (disabling never does), audited without customer data.

## 4. Subscriber import (background job) - REMOVED 2026-11-22

> **Superseded.** The CSV import panel, its server actions (`subscriber-imports.ts`), the worker (`subscriber-import-worker.ts`), the parser (`src/lib/subscriber-import.ts`), its poller job and its System Health row were removed as a redundant second way to add subscribers; "Add Bulk Subscribers" is unchanged. The `SubscriberImportJob` model, its enum and its migration are **kept** and no row was deleted. What follows is the historical description of what existed.

Parsing (`src/lib/subscriber-import.ts`): `email[,first[,last]]`, comma/semicolon/tab, optional header, quotes, BOM, CRLF; strict address validation; first of a duplicate wins; names stripped of control characters and markup and capped. **Limits: 250,000 rows and 4 MB per import** (4 MB because a list reaches the server as one Server Action body and `next.config.ts` caps those at 5 MB; this was 12 MB in the first draft, which the framework would have rejected with an opaque error - fixed in this audit). 4 MB is roughly 150,000 ordinary addresses, so a 250,000-row file only fits if rows are very short. **A 250,000-row import capacity is not a 250,000-email sending capacity** (section 7). **Measured and tested limits:** the size is measured in BYTES (`Buffer.byteLength`), not characters, so multi-byte text cannot slip past it; exactly 250,000 short rows are accepted (about 3.5 MB), 250,001 are refused with a message naming the limit, and a 4.5 MB multi-byte file is refused on size. The supported maximum is therefore the SMALLER of 250,000 rows and 4 MB (roughly 150,000 addresses once names are included). The worker holds one 4 MB payload and a 1,000-row slice at a time. These boundaries were tested with the in-memory database; **the runtime of a 250,000-row import on PostgreSQL has not been measured**, so the 250,000 figure is a configured ceiling, not a verified throughput.

The request only validates and queues. The worker (`subscriber-import-worker.ts`, run every minute) processes 1,000 rows per chunk with a cursor (`nextRow`): it creates only addresses with no subscriber row (`createMany skipDuplicates` against `@@unique(companyId, email)`), **never modifies an existing SUBSCRIBED / UNSUBSCRIBED / SUPPRESSED subscriber**, counts them instead, and advances counters with a compare-and-swap on the cursor so two workers cannot count a chunk twice. A failed chunk marks the job FAILED while keeping its payload and cursor; Resume continues. The error report is `row,reason` lines (fixed codes, no address, no name) - there is no formula-injection surface. Verified with an in-memory database (100,000 rows in 20 ticks; restart; double processing; failure; CAS); **not verified on PostgreSQL**.

## 5. Campaign builder

Blocks: heading, text, image, button, divider, spacer. Buttons, linked images and image sources accept only absolute `http(s)` URLs with a host and no credentials, no control or quote characters (javascript:, data:, vbscript:, file:, mailto:, relative and protocol-relative links are refused; 21 hostile inputs are tested). Author text is HTML-escaped; personalization (`{{firstName|there}}`, lastName, fullName, email) escapes the recipient's data and uses the fallback when empty; unknown fields and unfilled `[[placeholders]]` block queueing. The server re-validates on save, renders table-based inline-styled HTML, and runs it through the existing sanitizer; the preview is rendered by the server with the same shell, sanitizer and personalization the send uses, in a sandboxed iframe with a restrictive CSP. The shell adds the company footer and the unsubscribe link, which a design cannot remove. Drafts and every action are Administrator / Marketing Agent only and company-scoped. A test send goes to the signed-in user's own address with sample data and is independent of the subscriber list.

## 6. Queued campaign delivery

`DRAFT -> QUEUED | SCHEDULED -> SENDING -> SENT`, with `PAUSED` and `CANCELLED`. Queueing sends nothing. The worker (`campaign-worker.ts`, once a minute):

- Fixes the audience in keyset chunks of 1,000 into `MarketingCampaignSend` (unique `(campaignId, subscriberId)`; `skipDuplicates`).
- **Write-ahead claim**: PENDING -> UNKNOWN by compare-and-swap before the message leaves; a crash afterwards leaves UNKNOWN, which is never sent again automatically (shown as "Outcome unknown").
- Re-reads the **campaign status and the subscriber's current status before every recipient** (pause, cancel, unsubscribe and suppression take effect inside a running batch - added in this audit).
- Failure handling: a Gmail timeout or 5xx is ambiguous -> UNKNOWN; a definite failure retries after 5 min, then 30 min, up to 3 attempts, then FAILED; a provider rate-limit answer backs the row off for an hour and stops the batch without counting a failure; a disconnected sender pauses the whole campaign without marking anything failed.
- Limits: `CAMPAIGN_SENDS_PER_MINUTE` (default 20) and `CAMPAIGN_DAILY_LIMIT` (default 400, rolling 24 hours per sending account). Both are computed **from the database**, so instances sharing a database share them; the per-minute budget was per process in the first draft and is global now (it counts recent attempts, including in-flight ones). The count and the claims are separate statements, so two instances ticking in the same instant can overshoot by at most one batch.
- Statistics: waiting / sent / failed / outcome unknown / skipped. **"Sent" means accepted by Gmail.** Opens, clicks, bounces and inbox placement are not tracked; the panel says so.
- Scheduling: the time is entered in the browser's zone (now labelled) and stored as an exact UTC instant; the worker promotes SCHEDULED campaigns whose time has passed.

Verified with an in-memory database and a fake provider (33 tests: budgets, rolling cap, suppression at send time, unsubscribed mid-batch, retries, ambiguous outcomes, crash recovery, rate limit, disconnected sender, schedule, pause, concurrency, 3,000-subscriber run, shared budget). **Not verified on PostgreSQL and not verified against real Gmail.**

## 7. Provider capacity (facts, not promises)

Sending uses the campaign author's own connected Gmail through the Gmail API. Gmail allows a few hundred messages a day for a standard account (the exact limit depends on the account type and Google's policies, which change). At the default 400/day a 10,000-subscriber campaign takes about 25 days; **a list of hundreds of thousands cannot be sent through Gmail** and needs a transactional / bulk email provider (new vendor, new cost, new DNS/authentication work). That is a **DECISION** and an approval item; nothing was changed or selected.

## 9. Defects found and fixed by this audit

1. Customer addresses leaked through `loadMoreActivities` (a directly callable action) and the dashboard activity feed - now masked for restricted viewers.
2. The import size limit (12 MB) exceeded the Server Action body cap (5 MB) - now 4 MB with an honest message.
3. The campaign per-minute limit was per process - now shared through the database.
4. Pause / cancel / unsubscribe were only checked per pass, not per recipient - now per recipient.
5. Sequence post-send writes were not conditional on the step the worker had read, so a stale worker could overwrite a newer state - now conditional.
6. The poller logged the full error object (could carry a connection string or recipient) - now a category only; an in-flight sweep stops taking new work once shutdown is requested.
7. `/failed-signins`, `/leads`, `/quotes`, `/subscriptions` were not in the explicit no-store header list - added.
8. The schedule input did not say which time zone it used - now shown.
9. A test that depended on the time of day (24-hour window) was made independent of it.

## 11. Addendum 2026-11-22 (release-gate pass)

**Marketing Agent access (verified in code, unchanged).** `isMarketingOnly(role)` removes Dashboard, Contacts, Leads, Quotes, Bookings and Sequences from the Marketing Agent (`canViewDashboard`, `canViewContacts`, `canViewLeads`, `canViewQuotesPage`, `canViewBookings`, `canViewSequencesPage`), so global search, lists and pages that carry CRM customer addresses are closed to that role; `canViewSubscriptions` (Administrator and Marketing Agent) opens Subscriptions only, which reads the `Subscriber` table, never Contacts or Leads. The remaining exposure is of the marketing audience itself (subscriber addresses, unsubscribe reasons). A subscriber address can coincide with a customer's. **DECISION for the owner:** keep full subscriber addresses visible to Marketing Agents (current), or mask them for that role with a reveal like the customer one. Not changed.

**Campaign limits - exactly what is enforced (updated 2026-11-22).** Both limits are enforced in the database by `claimWithinQuota`: for each recipient, ONE transaction, serialised per sending account by a PostgreSQL advisory lock, counts what that sender's campaigns attempted in the last 55 seconds (in-flight claims included) against `CAMPAIGN_SENDS_PER_MINUTE` and what was sent or left uncertain (`UNKNOWN`) in the last 24 hours against `CAMPAIGN_DAILY_LIMIT`, and only then claims the row (compare-and-swap `PENDING` -> `UNKNOWN`). Concurrent ticks, workers or app instances therefore cannot exceed a limit: the earlier overshoot of one batch per simultaneous worker no longer exists by construction. The lock is held for those few statements only, never while a message is sent. Verified by in-memory concurrency tests (ten simultaneous workers claim exactly the budget; two senders have independent budgets; uncertain messages count against the daily cap; one row raced by many workers is claimed once); the same guarantee against real PostgreSQL is tested in `campaign-and-import.integration.test.ts` and has **not been run** (CI database job). Defaults (20 a minute, 400 a day) are unchanged; what Google actually allows is described in `COMPASS_CAMPAIGN_SENDING_CAPACITY.md`.

**Subscriber search by email (built 2026-11-22).** One function (`subscriberSearchWhere`) builds the search filter for the list, for the count shown when "select all matching" is confirmed and for the delete (`deleteSubscribersMatchingFilter`), so the three cannot disagree; the delete re-evaluates the text on the server with the caller's CURRENT email permission, and `excludeIds` can only narrow it. A complete address matches exactly (case-insensitive) for every viewer; any other text matches by substring only for a viewer who may see full addresses, and matches NOTHING (never everything) for a restricted viewer. Tests: `subscribers-privacy.test.ts` and the list component tests.

**System Health (added; since 2026-11-22 the row is named "Campaign delivery" and covers the campaign worker only, the import job having been removed).** One new row, "Subscriber imports and campaign delivery" (`checkMarketingWorkers`), read from the same in-process state as the sequence row: Healthy only when both jobs completed a run recently, Critical when either failed last time or is silent beyond 3 minutes (error category only), Warning when the poller is switched off, Unknown before the first tick. It reads state only. Per server process, like the sequence row. Tested (4 tests).

**Test discovery.** Vitest now lists exactly the test files that exist (365 at this point; `vitest list --filesOnly` equals a file-system search). An earlier full run reported 27 more files, all database-gated and all skipped; their origin was not identified (not present now). `vitest.config.ts` now excludes `.next`, `.open-next`, `.claude`, `.wrangler` and `docs` so build or tooling folders cannot contribute files to a run.

**Turbopack tracing warnings (`src/server/storage/local.ts`).** They were real, not noise: a path built from an environment-controlled directory makes the bundler trace the whole project into the standalone output (the file's own header says so). The three remaining expressions carry `/*turbopackIgnore: true*/` now (comments only, no behaviour change) and the build prints no warnings.

**Gmail / provider verification - status: completed with controlled mocks only.** Covered: send timeouts and dropped responses -> "ambiguous" (never retried, never marked failed), 5xx -> ambiguous, 401 or insufficient permission -> reconnect required and the connection marked revoked, 429 / rate-limit reasons -> a distinct rate-limit failure (campaigns back off an hour and stop the batch), an unreadable 2xx is still a success, refresh failures that are `invalid_grant` vs temporary, no token or recipient in any log line, credentials only read on the server and the refresh token stored encrypted. ## Release consolidation additions (2026-11-22)

* **Customer search** (`src/server/search/contact-search.ts`, used by the global search, Contacts, Leads and the task-link search): a COMPLETE email address finds the record by exact match (primary and secondary addresses) for every viewer, and the result still shows the masked address unless the viewer may see it; a fragment of an address is searched only for a viewer who may see full addresses (for a restricted viewer it would be an oracle that rebuilds a hidden address piece by piece); phone numbers match by digits however typed; names match word by word. Visibility filters are unchanged and still applied first. The search text is never logged by the module.
* **Subscriber address privacy:** a Marketing Agent without the unlimited switch sees masked addresses in the subscriber list and on a campaign's delivery list. There is **no reveal flow for subscribers** (a reveal needs its own allowance table, a migration and audit events): this needs your decision. An Administrator or a user with the switch sees full addresses.
* **Website signing v2** (`website-request-signature.ts`, `website-signature-guard.ts`): HMAC-SHA-256 over a length-prefixed message binding method, path, company, the exact body bytes and a one-time nonce; constant-time comparison; 120 s age and 30 s future window; the nonce is consumed by one atomic `INSERT ... ON CONFLICT DO NOTHING` (replays fail across instances); a refused signature never reaches the limiter; a verified visitor IP keys a per-visitor limit next to the unchanged account-wide budget; strict mode is the explicit switch `WEBSITE_SIGNATURE_REQUIRED=true` so the CRM can be deployed first; `LEAD_INGEST_SECRET_PREVIOUS` allows key rotation. Contract comparison with the website: `CRM_WEBSITE_API_COMPATIBILITY_VERIFICATION.md`. Log lines carry fixed tags only.
* **Campaign mail:** `List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) on every message, only for an https URL and header-injection safe; `POST /api/public/unsubscribe` accepts the mailbox provider's one-click request (token in the URL, idempotent, `EMAIL_ONE_CLICK`).
* **CI:** the checkout steps no longer keep the workflow token in `.git/config` (`persist-credentials: false`).
* **Reviewed and found sound (no change):** the Administrator-only, same-company, audited, step-up-protected unlimited-email switch (`updateUnlimitedCustomerEmailAccess`), read fresh from the database on every request so a change takes effect on the user's next request; the atomic 5-per-business-day reveal counter; the notification privacy rules.
