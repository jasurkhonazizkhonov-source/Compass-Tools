**First CI run on GitHub (commit `28a5262`, run 45014748069) and its correction.** Static checks, the Docker smoke test and the dependency audit passed. The "Unit + real-database integration tests" job failed although `npm ci`, `prisma migrate deploy` on an empty PostgreSQL 17 and the migration drift check had passed: Vitest's database safety gate (`src/test/integration-database-guard.ts`) refused to start ("the server answered from a non-loopback address"). Causes, established from the job output and reproduced locally where possible:

* **Why the gate refused.** CI published the database with `docker run -p 127.0.0.1:5432:5432`. The tests connect to loopback, Docker forwards the connection into the container, and the server's own address (`inet_server_addr()`) is then a container-network address, not loopback. A forwarded port looks exactly like a tunnel to somebody else's database, which is what the gate exists to refuse, so the gate was right and the CI service was wrong. (The address itself could not be read from the job output - the gate deliberately never prints it - so "a container-network address" is the explanation consistent with the evidence, to be confirmed by the next CI run.)
* **Why Vitest printed "No test files found".** A secondary effect: the exception thrown by the global setup aborts the project before discovery, and Vitest then prints that message first. Reproduced locally with the same command and an unreachable loopback database URL; without the database variables the same configuration discovers every file. There was no discovery problem.
* **Why TLS verification was off.** `NODE_TLS_REJECT_UNAUTHORIZED=0` was set for the whole job (so `npm ci` also ran without certificate checks). The only code that needed it was one `pg.Client` in `card-vault.integration.test.ts`, built from the URL alone: the pg driver reads `sslmode=require` as normal certificate verification, which a self-signed certificate fails. Everything else (the application client, the guard, the other tests) sets its own explicit policy.
* **The Vite warning** ("configLoader: 'native'") is informational: `vitest.config.ts` uses ESM syntax in a CommonJS package. It affects nothing today and is left alone (converting the config is an unrelated change).

Correction (`.github/workflows/ci.yml`, `src/test/integration-database-guard.ts`, tests): the CI database now runs with `--network host` and `listen_addresses=127.0.0.1`, so the server itself answers from 127.0.0.1; a new step fails the job unless every listener on port 5432 is loopback; the certificate now names 127.0.0.1 and is trusted for the test step only through `NODE_EXTRA_CA_CERTS`, and the job-wide verification switch is gone. The gate is **not** relaxed: it still accepts only 127.0.0.1 and ::1, only the database `compass_test` (admin: `postgres` on the same host and port), only literal loopback hosts (it performs no DNS lookups), and it now names the kind of an unacceptable address (container network, public, ...) without printing it. Its live half, which had no unit tests, now has them (`integration-database-guard.test.ts`), and `ci-database-isolation.test.ts` pins the workflow properties. None of this proves network isolation by itself: that is established by the job running and its loopback-listener step passing.
